# Глава 1. Архитектура: путь данных от колеса до карты

> **Цель главы:** увидеть робота целиком — из каких устройств он состоит, какие
> программы на них работают и как данные проходят от датчика до карты.

## 1.1. Железо

Робот собран из дешёвых и доступных деталей:

| Узел | Что это | Роль |
|---|---|---|
| Шасси гироскутера | два мотор-колеса 6.5″, плата на STM32F103 | привод |
| Плата управления гироскутера | перепрошита на [hoverboard-firmware-hack-FOC](https://github.com/EFeru/hoverboard-firmware-hack-FOC) | FOC-управление моторами, телеметрия |
| ESP32-S3-DevKitC-1 | микроконтроллер с Wi-Fi и USB | «мозжечок»: связывает всё железо с ПК |
| Лидар от робота-пылесоса | вращающийся дальномер, UART 115200 | скан 360° |
| MPU6050 | гироскоп + акселерометр, I2C | удержание курса при езде прямо |
| ПК с ROS 2 | ноутбук, мини-ПК или Raspberry Pi | SLAM, навигация, RViz |

Перед робота — сторона поворотного колеса (кастера). Начало системы координат
`base_link` — середина оси мотор-колёс.

## 1.2. Программы и где они работают

```
 ┌───────────── STM32 (плата гироскутера) ─────────────┐
 │ hoverboard-firmware-hack-FOC, VARIANT_USART         │
 │ принимает steer/speed, отдаёт об/мин колёс          │
 └──────────────────────┬──────────────────────────────┘
                        │ UART, кадры 0xABCD, HB_BAUD
 ┌──────────────────────▼──────────────────────────────┐
 │ ESP32-S3: firmware/esp32_bridge (PlatformIO)        │
 │  loop():   команды колёсам 20 Гц, одометрия 50 Гц   │
 │  lidarTask: скан кусками по 8 кадров                │◄── лидар (UART)
 │  IMU: удержание курса                               │◄── MPU6050 (I2C)
 └──────────────────────┬──────────────────────────────┘
                        │ протокол v2: Wi-Fi/UDP  или  USB/COBS
 ┌──────────────────────▼──────────────────────────────┐
 │ ПК, ROS 2                                           │
 │  esp32_bridge ──► /scan, /odom, TF odom→base_link   │
 │        ▲                                            │
 │        └── /cmd_vel ◄── velocity_smoother ◄── Nav2  │
 │  slam_toolbox ──► /map, TF map→odom                 │
 │  scan_to_cloud ──► octomap_server ──► /projected_map│
 └─────────────────────────────────────────────────────┘
```

Четыре уровня — четыре кодовые базы:

| Уровень | Где код | Язык, сборка |
|---|---|---|
| Плата гироскутера | `firmware/hoverboard-firmware-hack-FOC/` (git-подмодуль) | C, PlatformIO / STM32Cube, прошивка через ST-Link |
| ESP32-S3 | `firmware/esp32_bridge/` | C++ (Arduino), PlatformIO |
| ROS-пакеты | `src/esp32_bridge`, `src/hoverbot_nav`, `src/twist_converter` | C++ (rclcpp), colcon |
| Симуляция | `src/hoverbot_sim` | URDF/xacro, SDF, launch на Python |

## 1.3. Путь данных: три петли

Удобно думать о системе как о трёх петлях с разной скоростью.

**Петля привода (быстрая, 20 Гц, на ESP32).** ПК присылает желаемые скорости
колёс в мм/с. ESP32 пересчитывает их в пару `steer`/`speed`, понятную прошивке
FOC, при езде прямо подмешивает поправку курса по гироскопу и 20 раз в секунду
шлёт команду плате. Если команды от ПК не приходят 300 мс — колёса
останавливаются. Это главный предохранитель робота.

**Петля одометрии и скана (50 Гц / ~5 Гц).** Плата гироскутера сообщает
обороты колёс. ESP32 интегрирует их в позу `(x, y, θ)` и 50 раз в секунду
отсылает на ПК. Параллельно отдельная задача FreeRTOS читает лидар и шлёт
скан кусками. На ПК нода `esp32_bridge` превращает это в стандартные
сообщения ROS: `/odom`, `/scan` и TF `odom → base_link`.

**Петля карты и навигации (медленная, 1–20 Гц, на ПК).** slam_toolbox
сопоставляет сканы, строит `/map` и публикует поправку `map → odom`. Nav2
планирует путь по карте и выдаёт `/cmd_vel`, который замыкает петлю на привод.

## 1.4. Дерево систем координат (TF)

```
map ──(slam_toolbox)──► odom ──(esp32_bridge или gz DiffDrive)──► base_link ──(static)──► laser
```

- `map → odom` — **только** slam_toolbox. Это поправка, которая накапливает
  ошибку одометрии. Второй источник этого преобразования ломает замыкание
  петель (поэтому у моста параметр `publish_map_odom_tf` по умолчанию
  выключен, а `amcl`/`map_server` не запускаются).
- `odom → base_link` — одометрия. На роботе её публикует мост, в симуляции —
  плагин DiffDrive.
- `base_link → laser` — статическое положение лидара. На роботе — мост
  (параметр `lidar_xyz`), в симуляции — `robot_state_publisher` из URDF.

## 1.5. Симуляция как двойник

Пакет `hoverbot_sim` заменяет ESP32 и мост: Gazebo публикует **те же** топики
и кадры (`/scan`, `/odom`, `/cmd_vel`, `odom → base_link → laser`). Поэтому
настройки SLAM и Nav2 можно отлаживать в симуляции и переносить на робота без
изменений — меняется только `use_sim_time`.


## 1.7. Сборка за пять минут

```bash
cd ~/ros2_ws_
git submodule update --init                    # прошивка гироскутера
source /opt/ros/kilted/setup.bash
colcon build --symlink-install
source install/setup.bash
colcon test --packages-select esp32_bridge && colcon test-result --verbose
ros2 launch hoverbot_sim mapping.launch.py     # проверка: симуляция + SLAM
```

`--symlink-install` важен: launch-файлы, YAML и xacro подхватываются без
пересборки, достаточно перезапустить launch.

> **✎ Упражнение.** Запустите `mapping.launch.py`, в другом терминале —
> `ros2 run tf2_tools view_frames`. Найдите в получившемся PDF все четыре кадра
> из раздела 1.4 и подпишите, какая нода публикует каждое ребро.
