# Глава 5. Нода `esp32_bridge`

> **Цель главы:** разобрать устройство ноды `src/esp32_bridge/src/bridge_node.cpp`:
> потоки, транспорт, публикацию `/scan` и `/odom`, приём `/cmd_vel`, —
> и научиться настраивать её параметры.

## 5.1. Интерфейс ноды

Исполняемый файл `esp32_bridge`, имя ноды — `esp_bridge`.

| Направление | Имя | Тип | Частота |
|---|---|---|---|
| публикует | `/scan` | `sensor_msgs/LaserScan` | по обороту лидара, ~5 Гц |
| публикует | `/odom` | `nav_msgs/Odometry` | 50 Гц |
| публикует | TF `odom → base_link` | `tf2_msgs/TFMessage` | 50 Гц |
| публикует | static TF `base_link → laser` (и опц. `map → odom`) | | один раз |
| подписан | `/cmd_vel` | `geometry_msgs/Twist` | |
| сервис | `/reset_odom` | `std_srvs/Trigger` | |

Запуск отдельно:

```bash
ros2 run esp32_bridge esp32_bridge --ros-args -p transport:=udp -p host:=192.168.0.105
ros2 run esp32_bridge esp32_bridge --ros-args -p transport:=serial -p device:=/dev/ttyACM0
```

## 5.2. Структура пакета и сборка

`CMakeLists.txt` собирает две цели:

```cmake
# Разбор протокола — отдельная библиотека без ROS, чтобы тестировать её отдельно
add_library(esp32_protocol STATIC src/protocol.cpp)
add_executable(esp32_bridge src/bridge_node.cpp)
target_link_libraries(esp32_bridge esp32_protocol rclcpp::rclcpp ... Boost::boost)
```

Это главный архитектурный приём пакета: **вся логика, которую можно
проверить без ROS и без железа** (CRC, COBS, сборка оборота, раскладка по
углам, синхронизация часов, кинематика), вынесена в `esp32_protocol` и
покрыта gtest. В `bridge_node.cpp` остаётся только «клей»: сокеты, таймеры,
сообщения ROS.

Тесту дополнительно добавлен include-путь прошивки — так он видит
`protocol.h` ESP32 и проверяет совместимость.

## 5.3. Модель потоков

```
главный поток (rclcpp::spin)           поток io_context (Boost.Asio)
──────────────────────────             ─────────────────────────────
on_cmd_vel  ─┐                         async_receive / async_read
ping_timer   ├─ post_send() ──asio::post──► link_->send()
cmd_timer    │                         on_packet()
reset_srv   ─┘                           ├─ publish_odom()  → /odom, TF
log_stats   (читает под мьютексами)      ├─ on_scan_chunk() → /scan
                                         └─ on_pong()       → TimeSync
```

Правило одно: **сокет или порт трогает только поток `io_context`.** Колбэки
ROS не пишут в сокет сами, а через `asio::post` кладут задачу в очередь
сетевого потока. Так не нужны блокировки вокруг транспорта.

Общие данные, которые читают оба потока, защищены:

- `sync_` (`TimeSync`) — `sync_mutex_`;
- `loss_` (`LossCounter`) — `stats_mutex_`;
- счётчики `crc_errors_`, `incomplete_scans_` — `std::atomic`.

Публикация в ROS из чужого потока безопасна: `rclcpp::Publisher::publish`
потокобезопасен.

Почему не `rclcpp`-таймеры для сети? Asio даёт асинхронный приём без
опроса: пакет обрабатывается сразу по приходу, а не на следующем тике.

## 5.4. Транспорт

Абстрактный класс:

```cpp
class Transport {
  virtual void start(OnPacket on_packet) = 0;               // в потоке io_context
  virtual void send(const std::vector<uint8_t> & pkt) = 0;  // в потоке io_context
};
```

**`UdpTransport`.** Сокет открывается на случайном локальном порту. Адрес ESP32
резолвится из `host:port`. Принимаются только датаграммы **с адреса ESP32** —
посторонние игнорируются. Отправка `send_to` неблокирующая по сути; ошибки
выводятся не чаще раза в 2 с (`RCLCPP_WARN_THROTTLE`).

Важная деталь UDP-сборки: ESP32 не знает адреса ПК, пока не получит от него
пакет. Поэтому PING-таймер работает с самого старта — первый же PING
«регистрирует» ПК на ESP32.

**`SerialTransport`.** Открывает порт как 8N1 без управления потоком.
Скорость (`baud`) для встроенного USB S3 не важна, но задаётся для
совместимости с USB-UART-адаптерами. Входящий поток режет `CobsStream`.

При ошибке чтения/записи (выдернули кабель, ESP32 перезагрузилась) порт
закрывается, и через 1 с `retry()` пытается открыть его снова. Нода не
падает — достаточно вставить кабель обратно.

## 5.5. Обработка входящих пакетов

```cpp
void on_packet(const uint8_t * data, std::size_t len) {
  const auto pkt = parse_packet(data, len);
  if (!pkt) { ++crc_errors_; return; }
  loss_.add(pkt->seq);
  switch (pkt->type) {
    case type::kOdom: publish_odom(*pkt); break;
    case type::kScan: on_scan_chunk(*pkt); break;
    case type::kPong: on_pong(*pkt); break;
    case type::kLog:  RCLCPP_INFO(get_logger(), "[esp32] %s", ...); break;
    default: break;   // неизвестные типы — совместимость с будущими прошивками
  }
}
```

### Одометрия

`publish_odom` берёт позу `x, y, th` как есть (её интегрирует ESP32), строит
кватернион из угла и заполняет скорости:

```
v = (vL + vR) / 2           [мм/с → м/с: / 1000]
ω = (vR − vL) / wheel_base
```

Тот же заголовок (с меткой времени ESP, переведённой в время ПК) уходит в TF
`odom → base_link`. Ковариации не заполняются (нули) — slam_toolbox и Nav2
их не используют.

### Скан: от кусков к `LaserScan`

Сначала `ScanAssembler::add` складывает куски в оборот:

- кусок **нового** оборота при недособранном старом — старый выбрасывается
  (потерялся последний кусок);
- пропуск номера куска — оборот помечается `complete = false`, но
  публикуется (с дырой);
- кусок с флагом `LAST` — оборот готов.

Затем `bin_scan` раскладывает точки по угловым ячейкам:

```cpp
a = s + (e − s) · j / 7;          // угол j-й точки внутри кадра
if (mirror) a = −a;               // лидар вращается по часовой
a += yaw_deg;                     // поворот монтажа
bin = ((a + 180) mod 360) / шаг;  // ячейка; угол ячейки i = −π + i·шаг
ranges[bin] = min(ranges[bin], d) // в одну ячейку — ближняя точка
```

Почему не просто «точка № k → ячейка № k»? Лидар пылесоса крутится
неравномерно, а куски теряются. Раскладка **по настоящим углам**
гарантирует, что потерянный кусок даст пробел (`+inf`), а не сдвиг всех
следующих точек. Сдвинутый скан — худшее, что может случиться со SLAM.

Ячейки без измерений получают `+inf` — по REP-117 это «нет отражения»;
`intensities` = 1 там, где точка есть.

Метка времени `LaserScan` — **середина оборота**: точки сняты за всё время
от первого до последнего куска, середина минимизирует среднюю ошибку.
`scan_time` — длительность оборота.

## 5.6. Команды движения

```cpp
void on_cmd_vel(const Twist & msg) {
  last_cmd_ = wheel_speeds_mm(msg.linear.x, msg.angular.z, wheel_base_);
  last_cmd_time_ = now();
  post_send(type::kCmd, encode_command(last_cmd_[0], last_cmd_[1]));
}
```

Обратная кинематика дифференциального привода:

```
vL = v − ω · B/2
vR = v + ω · B/2         (мм/с, с насыщением в int16)
```

Пример из теста: v = 0.5 м/с, ω = 1 рад/с, B = 0.54 м → vL = 230, vR = 770.

**Повтор команды.** Таймер 50 мс (`resend_cmd`) повторяет последнюю команду,
пока с момента последнего `/cmd_vel` не прошло `cmd_timeout` (0.5 с). Зачем:

- UDP теряет пакеты, а ESP32 остановит колёса через 300 мс без команд;
- teleop шлёт `/cmd_vel` только при нажатии клавиши.

После `cmd_timeout` повтор прекращается, ESP32 через 300 мс останавливает
робота. Итог: **если источник команд умер, робот встанет не позже чем через
~0.8 с.**

> Отличие от симуляции: плагин Gazebo DiffDrive выполняет последнюю
> команду **бесконечно**, пока не придёт новая. В симуляции teleop надо
> останавливать клавишей `k`.

## 5.7. Статические TF

`publish_static_tf` один раз публикует `base_link → laser` из параметров
`lidar_xyz` (м) и `lidar_rpy_deg` (градусы). Если включён
`publish_map_odom_tf` — ещё и нулевой `map → odom` с предупреждением в лог.

> **⚠ Внимание.** `publish_map_odom_tf:=true` — **только** для просмотра в
> RViz без SLAM. Вместе со slam_toolbox два издателя `map → odom` спорят,
> и карта перестаёт замыкаться.

## 5.8. Диагностика

Каждые 10 с:

```
Связь: принято 2873, потеряно 12 (0.4%), ошибок CRC 0, неполных оборотов 1, RTT 3.2 мс
```

| Поле | Норма | Если плохо |
|---|---|---|
| потеряно | < 1 % (Wi-Fi), 0 (USB) | плохой сигнал, энергосбережение роутера, другой канал 2.4 ГГц |
| ошибок CRC | 0 | помехи в USB-кабеле, разные версии протокола |
| неполных оборотов | единицы | потери UDP; много — проверьте сеть |
| RTT | 2–10 мс (Wi-Fi), < 1 мс (USB) | > 30 мс — метки времени неточны |

`От ESP32 ничего не пришло` — неверный `host`, ESP32 не в сети, файрвол
на ПК блокирует UDP, или неверная прошивка (`usb` вместо `wifi`).

## 5.9. Справочник параметров

| Параметр | По умолчанию | Описание |
|---|---|---|
| `transport` | `udp` | `udp` или `serial` |
| `host` | `192.168.0.105` | IP ESP32 (udp) |
| `port` | `8888` | порт ESP32 (udp) = `UDP_PORT` |
| `device` | `/dev/ttyACM0` | порт (serial) |
| `baud` | `921600` | скорость (serial) |
| `frame_id` | `laser` | кадр скана |
| `odom_frame` / `base_frame` | `odom` / `base_link` | кадры одометрии |
| `range_min` / `range_max` | 0.05 / 16.0 | границы дальности в `LaserScan`, м |
| `lidar_mirror` | `true` | лидар вращается по часовой — отразить углы |
| `lidar_yaw_deg` | 180 | поворот нуля лидара относительно «вперёд» робота |
| `scan_bins` | 360 | число ячеек, шаг = 360°/bins |
| `lidar_xyz` | [0.10, 0, 0.17] | положение лидара от оси колёс, м |
| `lidar_rpy_deg` | [0, 0, 0] | наклон лидара, ° |
| `wheel_base` | 0.54 | колея = `WHEEL_BASE` прошивки |
| `cmd_timeout` | 0.5 | сколько повторять последнюю команду, с |
| `publish_map_odom_tf` | `false` | см. 5.7 |

### Как подобрать `lidar_mirror` и `lidar_yaw_deg`

1. Поставьте робота перед стеной в 1 м, RViz, Fixed Frame = `base_link`.
2. Стена должна быть по оси +X (красная ось). Если она сбоку или сзади —
   меняйте `lidar_yaw_deg` (шагом 90°).
3. Поверните робота на месте **влево** (против часовой). В кадре `odom`
   стены должны стоять неподвижно. Если они вращаются в 2 раза быстрее
   робота — инвертируйте `lidar_mirror`.

## 5.10. `robot.launch.py`

```bash
ros2 launch esp32_bridge robot.launch.py transport:=udp host:=<IP>
```

Запускает мост, slam_toolbox (через его штатный `online_async_launch.py`, с
`use_sim_time:=false` и параметрами `config/slam_param.yaml`) и RViz.
Аргументы: `transport`, `host`, `device`, `slam` (true/false), `rviz`
(true/false), `rviz_config`.

Почему slam_toolbox через чужой launch, а не `Node(...)`: начиная с Jazzy это
**lifecycle-нода**. Запущенная как обычная, она остаётся в состоянии
`unconfigured` и молчит. Штатный launch переводит её в `active` (гл. 8).
