# Глава 4. Протокол ESP32 ↔ ПК, версия 2

> **Цель главы:** знать формат каждого пакета, понимать, почему он устроен
> именно так, и уметь безопасно его менять.

Протокол реализован **дважды**:

| Сторона | Файл | Стиль |
|---|---|---|
| ESP32 | `firmware/esp32_bridge/include/protocol.h` | header-only, без динамической памяти |
| ПК | `src/esp32_bridge/include/esp32_bridge/protocol.hpp` + `src/protocol.cpp` | `std::vector`, `std::optional`, без ROS |

Тест `src/esp32_bridge/test/test_protocol.cpp` подключает **оба** файла и
проверяет, что пакет, собранный одной стороной, разбирается другой.

## 4.1. Требования, из которых вырос протокол

1. **Wi-Fi теряет пакеты.** Старые данные не нужны — нужны свежие. Значит, UDP,
   а не TCP: TCP задержал бы свежую одометрию, пока переотправляет старую.
2. **Время измерения важнее времени прихода.** Задержка Wi-Fi гуляет на
   десятки миллисекунд; SLAM, получив скан со сдвинутой меткой, «размажет»
   стены. Поэтому каждый пакет несёт **время ESP32**, а ПК переводит его в своё.
3. **Один код на UDP и USB.** Пакет одинаков; различается только кадрирование.
4. **Целостность.** CRC16 на каждый пакет.
5. **Обнаружение потерь.** Сквозной номер пакета.

## 4.2. Формат пакета

Все поля little-endian.

```
 0      1      3                     11              N-2     N
 ┌──────┬──────┬─────────────────────┬───────────────┬───────┐
 │ type │ seq  │       stamp         │    payload    │ crc16 │
 │  u8  │ u16  │        u64          │   0…499 байт  │  u16  │
 └──────┴──────┴─────────────────────┴───────────────┴───────┘
        заголовок 11 байт                              2 байта
```

- `type` — тип пакета (таблица ниже). Старший бит 1 — направление ПК → ESP.
- `seq` — номер пакета отправителя, растёт на 1, переполняется через 65535.
- `stamp` — время отправителя: у ESP32 — **микросекунды** с загрузки
  (`esp_timer_get_time()`), у ПК — **наносекунды** его часов.
- `crc16` — CRC-16/Modbus: полином `0xA001` (отражённый), старт `0xFFFF`, по всем
  байтам перед CRC.

Максимальный размер пакета — `MAX_PACKET = 512` байт.

## 4.3. Типы пакетов

### ESP32 → ПК

| Код | Имя | Payload |
|---|---|---|
| `0x01` | ODOM | 5 × float32: `x` м, `y` м, `th` рад, скорость левого колеса мм/с, правого мм/с |
| `0x02` | SCAN | кусок оборота лидара, см. ниже |
| `0x03` | PONG | u64 — `stamp` из PING, возвращённый как есть |
| `0x04` | LOG | текст UTF-8 |

### ПК → ESP32

| Код | Имя | Payload |
|---|---|---|
| `0x81` | CMD | i16 скорость левого колеса, i16 правого, мм/с |
| `0x82` | PING | пусто; время ПК — в `stamp` заголовка |
| `0x83` | RESET_ODOM | пусто |

### Пакет SCAN подробно

```
 rev u16 | chunk u8 | flags u8 | кадр 0 | кадр 1 | … | кадр N−1
```

- `rev` — номер оборота лидара;
- `chunk` — номер куска внутри оборота, с 0;
- `flags`, бит 0 — `LAST`: последний кусок оборота;
- кадр — 20 байт: угол начала u16 (сотые градуса), угол конца u16,
  8 дистанций u16 в мм (0 — нет измерения).

Обычно в куске 8 кадров (164 байта payload), в последнем — сколько осталось.
`stamp` пакета SCAN — время прихода **первого** кадра куска.

Почему кусками, а не целым оборотом? Оборот — около 45 кадров ≈ 900 байт;
одна потеря UDP-датаграммы съела бы весь скан. С кусками пропадает 1/6
оборота, а остальное доходит.

## 4.4. Кадрирование

**UDP:** один пакет = одна датаграмма. Границы даёт сам UDP.

**USB:** байтовый поток без границ. Пакет кодируется **COBS** (Consistent
Overhead Byte Stuffing) и завершается байтом `0x00`.

COBS убирает из данных все нули: каждый ноль заменяется числом — расстоянием
до следующего нуля. Тогда `0x00` можно использовать как разделитель. Накладные
расходы — 1 байт на каждые 254 байта данных. Пример:

```
данные:  11 22 00 33
COBS:    03 11 22 02 33       (03 — «через 3 байта ноль», 02 — «через 2 — конец»)
в поток: 03 11 22 02 33 00
```

Если ПК подключился посреди пакета, первый кусок до `0x00` будет битым —
COBS или CRC его отбросят, а дальше поток синхронизирован.

## 4.5. Синхронизация часов

Нода раз в 0.5 с шлёт PING со своим временем `t1` в `stamp`. ESP32 отвечает
PONG: в `stamp` заголовка — своё время `e`, в payload — `t1`. Нода получает
ответ в момент `t2`.

```
ПК   t1 ──PING──►            ◄──PONG── t2
ESP              e (ответ)
```

Считаем, что ESP ответила посередине пути:

```
rtt    = t2 − t1
offset = t1 + rtt/2 − e·1000           (нс)
время_ПК(e') = e'·1000 + offset
```

Ошибка такой оценки не больше `rtt/2`. Поэтому `TimeSync` хранит 16
последних замеров и использует замер с **наименьшим** `rtt` — у него
меньше всего неопределённость. На хорошем Wi-Fi лучший RTT 2–5 мс, значит
метки точны до 1–3 мс.

Пока ни одного PONG не пришло, нода ставит время прихода пакета.

## 4.6. Подсчёт потерь

`LossCounter` смотрит на разницу соседних `seq`:

- разница 1 — норма;
- 0 — дубликат, не считается;
- от 2 до 999 — потеряно `разница − 1` пакетов;
- ≥ 1000 — ESP32 перезагрузилась или пакеты переставились; не считаем.

Арифметика по модулю 2¹⁶ (`uint16_t`) корректно переживает переполнение.

## 4.7. Как изменить протокол

Пример: добавить напряжение батареи в ODOM.

1. **Спецификация.** Обновите комментарий в начале `protocol.h` (это
   единственное полное описание формата).
2. **ESP32.** `main.cpp`, `sendOdom()`: массив из 6 float.
3. **ПК.** `protocol.hpp` — поле в `OdomSample`; `protocol.cpp`,
   `parse_odom()` — проверка длины `6 * sizeof(float)`.
4. **Нода.** Использовать поле (например, публиковать
   `sensor_msgs/BatteryState`).
5. **Тест.** Обновите `TEST(Odom, ParsesFiveFloats)` и добавьте проверку,
   что пакет, собранный `proto::build` прошивки, разбирается `parse_odom`.
6. **Прошейте ESP32 и пересоберите ноду вместе.** Старая прошивка со новой
   нодой даст молчащий `/odom`: длина не совпадёт, пакеты будут отброшены.

Правила совместимости, заложенные в код:

- Неизвестные типы пакетов нода **игнорирует** (`default: break` в
  `on_packet`) — можно добавлять новые типы, не ломая старые ноды.
- Изменение длины существующего payload — несовместимое изменение. Если
  нужна совместимость, заведите новый тип (например, `0x05 ODOM2`).

## 4.8. Тесты протокола

```bash
colcon build --packages-select esp32_bridge
./build/esp32_bridge/test_protocol                        # все
./build/esp32_bridge/test_protocol --gtest_filter='Cobs*' # группа
```

| Тест | Что проверяет |
|---|---|
| `Crc16.ModbusReferenceVector` | CRC совпадает с эталоном Modbus |
| `Packet.FirmwareBuiltParsedByNode` / `NodeBuiltParsedByFirmware` | совместимость сторон |
| `Packet.CorruptedRejected`, `TooShortRejected` | битые пакеты отбрасываются |
| `Cobs.*`, `CobsStream.*` | кодирование, совместимость с прошивкой, мусор в потоке |
| `ScanAssembler.*` | сборка оборота, потеря среднего и последнего куска |
| `BinScan.*` | раскладка по углам, зеркало, поворот, «ближняя точка побеждает» |
| `TimeSync.UsesSampleWithSmallestRtt` | выбор лучшего замера |
| `Command.DiffDriveKinematics` | `/cmd_vel` → скорости колёс |
| `LossCounter.CountsGapsAndWraparound` | потери и переполнение `seq` |

> **✎ Упражнение.** Посчитайте вручную CRC-16/Modbus для строки
> `"123456789"`. Должно получиться `0x4B37` — это и есть эталон из первого
> теста.
