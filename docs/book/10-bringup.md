# Глава 10. Первый запуск железа, калибровка, диагностика

> **Цель главы:** пройти путь от собранных проводов до робота, который сам
> едет по карте, — безопасно и по шагам. Каждый шаг проверяет одну вещь.

> **⚠ Внимание.** Гироскутер — это два мотора по 250–350 Вт на 36 В. Ошибка в
> знаке скорости превращает робота в таран. Пока не пройден шаг 5, колёса
> должны быть **в воздухе** (робот на подставке), а рука — на выключателе.

## Шаг 0. Сверка конфигурации (железо не нужно)

```bash
scripts/hardware_bringup.sh check
```

Скрипт сравнивает:

- колею и диаметр: `config.h` ↔ параметр `wheel_base` ↔ xacro;
- скорость UART: `HB_BAUD` ↔ `USART*_BAUD` прошивки FOC;
- пины ESP32 на запрещённых GPIO 26–37;
- наличие `secrets.h`;
- совпадение `slam_sim.yaml` и `slam_param.yaml`.

На текущем состоянии репозитория скрипт **сообщит о двух проблемах** —
скорости UART (гл. 2.3) и пинах лидара (гл. 3.4). Исправьте их до шага 1.

## Шаг 1. Прошивки

1. Плата гироскутера: `VARIANT_USART`, нужная скорость UART (гл. 2.4).
2. ESP32-S3: `pio run -e wifi -t upload` или `-e usb` (гл. 3.3).

## Шаг 2. Провода

По `firmware/esp32_bridge/PINOUT.md`:

| От | К ESP32-S3 |
|---|---|
| TX левого кабеля сайдборда | GPIO 18 |
| RX левого кабеля сайдборда | GPIO 17 |
| GND кабеля сайдборда | GND |
| **15 В кабеля сайдборда** | **никуда — заизолировать** |
| TX лидара | свободный GPIO (например 4), = `LIDAR_RX_PIN` |
| питание лидара | внешние 5 В (не 3V3 ESP32 — мотор лидара) |
| MPU6050 SDA / SCL | GPIO 8 / 9, питание 3V3 |

Земли всех устройств соединены.

## Шаг 3. Связь без движения

```bash
scripts/hardware_bringup.sh link udp 192.168.0.105
# или: scripts/hardware_bringup.sh link serial /dev/ttyACM0
```

Запускает только мост (без SLAM и RViz) и через 8 с меряет частоты.

| Проверка | Ожидание |
|---|---|
| в логе `[esp32] alive: imu=1 link=1` каждые 5 с | связь есть, IMU найден |
| `/odom` | ≈ 50 Гц |
| `/scan` | ≈ 5 Гц (скорость вращения лидара) |
| TF `odom → base_link` | есть |
| строка `Связь: …` | потери < 1 %, CRC 0 |

`/imu` скрипт тоже проверяет, но реальный робот его не публикует — «НЕТ
данных» для `/imu` нормально.

Покрутите колесо рукой вперёд: `ros2 topic echo /odom --field pose.pose.position`
— `x` должен **расти**. Если уменьшается — знак колеса (гл. 2.3, «Направление
вращения»).

| Неисправность | Куда смотреть |
|---|---|
| `От ESP32 ничего не пришло` | IP, сеть 2.4 ГГц, сборка `wifi`/`usb`, файрвол ПК режет входящий UDP от ESP32 (нода слушает случайный порт — проще временно `sudo ufw disable` для проверки) |
| `/odom` есть, но стоит на месте | скорость UART плата ↔ ESP32; провода TX/RX перепутаны |
| `/scan` нет | пин лидара; питание мотора лидара; `LIDAR_BAUD` |
| `imu=0` | провода MPU6050; пины 8/9 |
| нет доступа к `/dev/ttyACM0` | `sudo usermod -aG dialout $USER`, перелогиниться |

## Шаг 4. Колёса на подставке

```bash
ros2 run teleop_twist_keyboard teleop_twist_keyboard
```

С колёсами в воздухе:

1. `i` (вперёд) — оба колеса крутятся вперёд.
2. `j` (влево) — левое назад, правое вперёд (поворот против часовой).
3. Закройте teleop (Ctrl+C) во время движения — колёса **должны
   остановиться** не позже чем через ~1 с (повтор 0.5 с + таймаут ESP32 0.3 с).
4. Wi-Fi: выключите Wi-Fi на ПК во время движения — то же.

Если поворот перепутан — проверьте знак `steer` (гл. 3.6, `hbUpdate`).

## Шаг 5. Калибровка одометрии на полу

Одометрия — фундамент SLAM. Без калибровки следующие шаги бессмысленны.

**Длина (диаметр колеса).**

```bash
ros2 service call /reset_odom std_srvs/srv/Trigger
```

Проедьте ровно 2 м по рулетке. Если одометрия показала `x_изм`:

```
WHEEL_DIAMETER_новый = WHEEL_DIAMETER × 2.0 / x_изм
```

**Поворот (колея).** Обнулите одометрию, разверните робота на месте на 5
полных оборотов (метка на полу). Если одометрия насчитала угол `θ_изм`
(сложите обороты: `th` — в пределах ±π):

```
WHEEL_BASE_новый = WHEEL_BASE × θ_изм / (5 · 2π)
```

Новый `WHEEL_BASE` впишите в **три** места: `config.h`, параметр
`wheel_base` (умолчание в `bridge_node.cpp` или launch), `wheel_separation`
в xacro. Диаметр — в `config.h` и `wheel_radius` в xacro. Перепрошейте ESP32
и запустите `hardware_bringup.sh check`.

**Лидар.** RViz, Fixed Frame = `odom`, `/scan` с Decay Time 10 с. Медленно
поверните робота на месте. Стены должны стоять на месте. Если вращаются —
`lidar_mirror` / `lidar_yaw_deg` (гл. 5.9).

## Шаг 6. Карта

```bash
scripts/hardware_bringup.sh map udp 192.168.0.105
ros2 run teleop_twist_keyboard teleop_twist_keyboard     # в другом терминале
```

Ездите медленно (0.2–0.3 м/с), повороты плавно. Сделайте петлю по
помещению и вернитесь в начало — карта должна «защёлкнуться».
Сохраните: `ros2 run nav2_map_server map_saver_cli -f ~/map`.

## Шаг 7. Навигация

```bash
scripts/hardware_bringup.sh nav udp 192.168.0.105
```

Скрипт попросит подтверждения Enter. Первая цель — 1 м прямо перед роботом в
свободном пространстве. Затем — подбор скоростей (`desired_linear_vel`,
`max_velocity`), `inflation_radius` под ваши двери и footprint под реальные
габариты (гл. 9).

## Сводная диагностика

| Команда | Что показывает |
|---|---|
| `ros2 topic hz /scan` / `/odom` | частоты |
| `ros2 run tf2_ros tf2_echo map base_link` | где робот на карте |
| `ros2 run tf2_tools view_frames` | PDF дерева TF |
| `ros2 lifecycle get /slam_toolbox` | `active` |
| `ros2 topic info -v /scan` | издатели, подписчики и их QoS |
| лог моста `Связь: …` | потери, CRC, RTT |

**ROS-команды зависают** (после `kill -9`): `fastdds shm clean`; если не
помогло — `export FASTDDS_BUILTIN_TRANSPORTS=UDPv4` в каждом терминале.
