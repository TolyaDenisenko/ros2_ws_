# Глава 3. Прошивка ESP32-S3

> **Цель главы:** разобрать код `firmware/esp32_bridge/` построчно по смыслу,
> научиться его настраивать (пины, геометрия, Wi-Fi), собирать и заливать
> обе версии — `wifi` и `usb`.

## 3.1. Роль ESP32 в системе

ESP32-S3 — посредник между «медленным» ПК и «быстрым» железом. ПК может
подвиснуть, Wi-Fi может потерять пакет, а колёса должны остановиться вовремя.
Поэтому на ESP32 живёт всё, что требует жёсткого реального времени:

- передача команд плате гироскутера 20 раз в секунду;
- аварийная остановка через 300 мс без команд;
- интегрирование одометрии по каждому кадру телеметрии (100 Гц);
- чтение лидара без пропусков байтов;
- метка времени каждого измерения по своим часам.

## 3.3. Сборка: две прошивки из одного кода

```ini
[env]
platform = espressif32
board = esp32-s3-devkitc-1
framework = arduino
lib_deps = electroniccats/MPU6050@^1.4.1
build_flags =
    -std=gnu++17
    -DARDUINO_USB_CDC_ON_BOOT=1    ; Serial = встроенный USB ESP32-S3
    -DARDUINO_USB_MODE=1

[env:wifi]
build_flags = ${env.build_flags} -DTRANSPORT_WIFI

[env:usb]
build_flags = ${env.build_flags} -DTRANSPORT_USB
```

Общая секция `[env]` наследуется обоими окружениями; они отличаются одним
флагом. `transport.h` проверяет, что задан ровно один:

```cpp
#if defined(TRANSPORT_WIFI) == defined(TRANSPORT_USB)
#error "Задайте ровно один из флагов: -DTRANSPORT_WIFI или -DTRANSPORT_USB"
#endif
```

Какую выбрать:

| | `wifi` | `usb` |
|---|---|---|
| Где ПК | отдельно, ноутбук на столе | на тележке (мини-ПК, Raspberry Pi) |
| Канал | UDP, порт 8888 | USB CDC, `/dev/ttyACM0` |
| Потери | возможны, протокол их переживает | практически нет |
| Отладочный монитор `pio device monitor` | можно | нельзя: порт занят протоколом |

### Команды

```bash
cd firmware/esp32_bridge
cp include/secrets.example.h include/secrets.h   # один раз, вписать сеть
pio run -e wifi -e usb                           # собрать обе
pio run -e wifi -t upload                        # залить Wi-Fi-версию
pio run -e usb  -t upload --upload-port /dev/ttyACM0
```

Если `pio` не в `PATH` — `~/.platformio/penv/bin/pio`. Шить через порт
**USB** платы (встроенный USB S3). Если плата не входит в режим прошивки:
зажать **BOOT**, нажать **RST**, отпустить **BOOT**.

## 3.4. Настройка: `config.h`

Это единственный файл, который обычно правят.

### Плата гироскутера

```cpp
#define HB_SERIAL Serial2
constexpr uint32_t HB_BAUD = 1000000;   // = USART*_BAUD прошивки FOC!
constexpr int HB_RX_PIN = 18;           // ← TX сайдборд-кабеля
constexpr int HB_TX_PIN = 17;           // → RX сайдборд-кабеля
```

`HB_BAUD` обязан совпадать с `USART2_BAUD` платы (гл. 2.3). Сейчас **не
совпадает** с заводским 115200 — исправьте одну из сторон.

### Лидар

```cpp
#define LIDAR_SERIAL Serial1
constexpr uint32_t LIDAR_BAUD = 115200;
constexpr int LIDAR_RX_PIN = 32;   // ⚠
constexpr int LIDAR_TX_PIN = 33;   // ⚠
```

> **⚠ Внимание: пины лидара.** Они достались от прошивки для обычного ESP32.
> У ESP32-S3 GPIO 26–32 — линии флеш-памяти, 33–37 — PSRAM на модулях
> `…R8`. Использовать их нельзя: в лучшем случае лидар молчит, в худшем —
> плата не загружается. Переключите провод данных лидара на свободный
> пин и поправьте константы:
>
> ```cpp
> constexpr int LIDAR_RX_PIN = 4;
> constexpr int LIDAR_TX_PIN = 5;
> ```
>
> Свободные и безопасные GPIO S3: **1, 2, 4–18, 21, 38–42, 47, 48**
> (подробности — `PINOUT.md`). TX лидару не нужен (он ничего не принимает),
> но UART требует номер пина.

### IMU

```cpp
constexpr int IMU_SDA_PIN = 8;
constexpr int IMU_SCL_PIN = 9;
constexpr float YAW_KP = 0.8f;   // усиление удержания курса
```

Раньше было 21/22, и IMU не работал: у S3 нет GPIO 22.

### Геометрия — должна совпадать с ROS

```cpp
constexpr float WHEEL_BASE = 0.54f;       // колея по центрам шин, м
constexpr float WHEEL_DIAMETER = 0.16f;   // диаметр колеса, м
constexpr float RPM_TO_MPS = M_PI * WHEEL_DIAMETER / 60.0f;
```

`RPM_TO_MPS`: колесо за один оборот проходит `π·D` метров, об/мин делим на
60 — получаем м/с. Для D = 0.16: 1 об/мин ≈ 8.4 мм/с.

`WHEEL_BASE` = параметр `wheel_base` моста = `wheel_separation` в xacro.
`WHEEL_DIAMETER` = 2 × `wheel_radius` в xacro. Полная таблица — приложение A.

### Тайминги и связь

```cpp
constexpr uint32_t CMD_TIMEOUT_MS   = 300;  // нет команд — стоп
constexpr uint32_t HB_CMD_PERIOD_MS = 50;   // команды плате, 20 Гц
constexpr uint32_t ODOM_PERIOD_MS   = 20;   // одометрия на ПК, 50 Гц
constexpr uint16_t UDP_PORT = 8888;
constexpr uint32_t USB_BAUD = 921600;       // для встроенного USB не важна
```

`CMD_TIMEOUT_MS` должен быть заметно больше периода повтора команд мостом
(50 мс): тогда потеря одного-двух UDP-пакетов не дёргает робота.

### Wi-Fi: `secrets.h`

```cpp
constexpr char WIFI_SSID[] = "my_wifi";
constexpr char WIFI_PASS[] = "my_password";
```

ESP32-S3 работает только в **2.4 ГГц**. IP платы выдаёт роутер — закрепите
его за MAC-адресом платы (DHCP reservation), иначе после перезагрузки
придётся искать новый адрес.

## 3.5. Разбор `transport.h`

Класс `Transport` прячет канал связи. Наружу — четыре метода:

| Метод | Назначение |
|---|---|
| `begin()` | поднять Wi-Fi + UDP-сокет или USB-порт |
| `poll(out, max)` | вернуть **один** целый пакет протокола или 0 |
| `accept_sender()` | запомнить, кому отвечать (UDP) |
| `send(pkt, len)` | потокобезопасно отправить пакет |

**Wi-Fi.** `begin()` включает режим станции, **отключает энергосбережение
модема** (`WiFi.setSleep(false)` — без этого задержка скачет до сотен
миллисекунд) и открывает UDP-порт 8888. Адрес ПК заранее не известен:
ESP32 отвечает тому, кто прислал ей корректный пакет. Именно поэтому
`accept_sender()` вызывается **после проверки CRC** — случайный мусор из сети
не «перехватит» робота. Пока ни одного пакета от ПК не было, `send()` молчит.

**USB.** Байты копятся в `rx_`, пока не придёт `0x00`; затем буфер
декодируется из COBS. Переполнение (мусор без разделителей) помечается флагом,
и кадр выбрасывается целиком. При отправке `Serial.setTxTimeoutMs(0)` и
проверка `availableForWrite()` гарантируют, что прошивка **никогда не ждёт
ПК**: если ПК не читает порт, пакеты просто теряются, а колёса продолжают
управляться.

`send()` защищён мьютексом FreeRTOS: её вызывают и `loop()`, и задача лидара.

## 3.6. Разбор `main.cpp`

### Отправка пакетов

```cpp
static void sendPacket(uint8_t type, uint64_t stamp, const void * payload, size_t len)
{
  uint8_t b[proto::MAX_PACKET];        // на стеке вызывающей задачи
  ...
  portENTER_CRITICAL(&seqMux);
  const uint16_t seq = txSeq++;        // общий счётчик — под критической секцией
  portEXIT_CRITICAL(&seqMux);
  const size_t n = proto::build(b, type, seq, stamp, payload, len);
  pc.send(b, n);
}
```

Буфер на стеке, а не глобальный, — чтобы две задачи не портили данные друг
друга. Номер `seq` один на все типы пакетов: по пропускам нода считает потери.

`logf()` — `printf` на ПК: сообщение уходит пакетом `LOG` и появляется в логе
ноды с префиксом `[esp32]`. Это единственный способ отладки в USB-сборке.

### Команда плате: `hbSend` и `hbUpdate`

```cpp
static void hbUpdate()
{
  const float vl = tgtL / 1000.0f, vr = tgtR / 1000.0f;   // мм/с → м/с
  const float lin = (vl + vr) * 0.5f;                     // линейная, м/с
  float ang = (vl - vr) / WHEEL_BASE;                     // > 0 — поворот вправо
  if (straightMode && fabsf(lin) > 0.05f) {
    const float err = /* straightTargetYaw − imuYaw(), нормированный в ±π */;
    ang += constrain(err * YAW_KP, -0.5f, 0.5f);
  }
  hbSend(constrain(ang * 400, -1000, 1000),               // steer
         constrain(lin * 600, -1000, 1000));              // speed
}
```

1. С ПК приходят скорости колёс. Их переводят обратно в линейную `lin` и
   угловую `ang` скорости — то, что понимает микшер FOC.
2. Знак `ang = (vl − vr)/B` выбран под микшер платы: `steer > 0` ускоряет
   левое колесо (гл. 2.2).
3. **Удержание курса.** Если оба колеса крутятся с одинаковым модулем скорости
   (разница < 10 мм/с), включается `straightMode`: запоминается курс по
   гироскопу, и П-регулятор с коэффициентом `YAW_KP` добавляет поворот,
   компенсирующий увод. Поправка ограничена ±0.5 рад/с.
4. Коэффициенты **400** и **600** переводят рад/с и м/с в единицы −1000…1000
   режима `VLT_MODE`. Подобраны вручную; при смене режима платы их
   пересчитывают (упражнение гл. 2).

`hbSend` собирает 8-байтный кадр `0xABCD, steer, speed, XOR`.

### Телеметрия и одометрия: `hbReadFeedback`

Разбор идёт **побайтно** с поиском маркера: если байт потерялся, кадр будет
отброшен по контрольной сумме, а следующий найдётся по `CD AB`:

```cpp
if (len == 0 && b != 0xCD) continue;                       // ждём младший байт 0xABCD
if (len == 1 && b != 0xAB) { len = (b == 0xCD); continue; } // повторный 0xCD — новый старт
```

Затем — интегрирование дифференциального привода:

```cpp
const float vr =  (int16_t)w[3] * RPM_TO_MPS;   // speedR_meas
const float vl = -(int16_t)w[4] * RPM_TO_MPS;   // левый мотор стоит зеркально
const float v   = (vl + vr) / 2;                // линейная скорость
const float w_z = (vr - vl) / WHEEL_BASE;       // угловая (против часовой > 0)
odomX += v * cos(odomTh) * dt;
odomY += v * sin(odomTh) * dt;
odomTh = wrap(odomTh + w_z * dt);
```

Это стандартная модель: робот за малое `dt` проезжает `v·dt` в направлении
`θ` и поворачивается на `ω·dt`. Ошибки в `WHEEL_DIAMETER` дают ошибку длины,
в `WHEEL_BASE` — ошибку поворота (калибровка — гл. 10).

### Команды от ПК: `handlePacket`

| Тип | Действие |
|---|---|
| `CMD` | запомнить `tgtL`/`tgtR`, обновить `lastCmdMs`, решить про `straightMode` |
| `PING` | ответить `PONG` со своим временем и временем ПК из запроса |
| `RESET_ODOM` | обнулить `x, y, θ`, сообщить в лог |

### Лидар: задача FreeRTOS

Лидар пылесоса шлёт пакеты по 36 байт:

```
55 AA 03 08 | скорость u16 | угол начала u16 | 8 × (дистанция u16, качество u8) | угол конца u16 | 2 байта
```

Последние 2 байта тела (обычно контрольная сумма) прошивка не проверяет —
битые пакеты отсеиваются по разбросу углов.

Углы кодируются как `(raw − 0xA000) / 64` градусов. `lidarTask`:

1. `lidarSync()` ищет заголовок `55 AA 03 08` (таймаут 200 мс).
2. Запоминает время прихода `stamp` и дочитывает 32 байта тела.
3. Отбрасывает пакет, если разброс углов больше 20° — признак битых данных.
4. Точки с качеством ниже `INTENSITY_MIN = 2` заменяет на 0 («нет измерения»).
5. Упаковывает 8 точек в кадр 20 байт (углы в сотых градуса + 8 дистанций в мм).
6. Копит 8 кадров и отправляет пакет `SCAN`. Время пакета — время **первого**
   кадра.
7. Когда угол начала «перескакивает» через 0° (и в обороте уже ≥30 кадров),
   отправляет хвост с флагом `LAST` и увеличивает номер оборота `rev`.

Почему отдельная задача: `lidarSync` ждёт байты с `delay(1)`. В `loop()` это
тормозило бы команды колёсам. Задача закреплена за ядром 1 с приоритетом 2.

### `setup()` и `loop()`

```cpp
void setup() {
  pc.begin();
  HB_SERIAL.begin(HB_BAUD, SERIAL_8N1, HB_RX_PIN, HB_TX_PIN);
  mpuOk = initImu();          // калибровка гироскопа: робот должен СТОЯТЬ
  xTaskCreatePinnedToCore(lidarTask, "lidar", 4096, nullptr, 2, nullptr, 1);
}

void loop() {
  принять все пакеты от ПК;
  если команд нет > 300 мс → tgtL = tgtR = 0;
  каждые 50 мс → hbUpdate();
  hbReadFeedback();
  каждые 20 мс → sendOdom();
  каждые 5 с → logf("alive: imu=%d link=%d");
  delay(1);
}
```

> **⚠ Внимание.** При включении `initImu()` калибрует гироскоп и
> акселерометр. Если робот в этот момент двигается или его держат в руках,
> удержание курса будет уводить в сторону. Включайте питание, когда робот
> стоит на полу.

## 3.7. Проверка прошивки

1. Wi-Fi-сборка: `pio device monitor` не покажет пакеты (они уходят по UDP), но
   покажет сообщения загрузчика — полезно, если плата перезагружается.
2. Запустите только мост (гл. 5): `ros2 run esp32_bridge esp32_bridge --ros-args
   -p transport:=udp -p host:=<IP>`. Каждые 5 с в логе должно появляться
   `[esp32] alive: imu=1 link=1`. `imu=0` — проверьте провода MPU6050 и пины.
3. Крутите колесо рукой — `ros2 topic echo /odom` должен меняться.
